# dbstore

The controller's embedded SQLite store — see the package doc comment in
`db.go` for what it holds. This directory is a mix of hand-written and
generated code; know which is which before editing:

| Path | What it is |
|---|---|
| `db.go`, `identity.go`, `phones.go`, `clips.go`, `segments.go`, `regroup.go`, `migrate.go` | **Hand-written.** `Store`'s domain-shaped API (`ClipState`, `Segment`, `Clip`, `ed25519.PublicKey`, `ErrNotFound`, ...) — edit these for behavior changes. |
| `schemas/db/*.sql` | **Hand-written.** goose migrations — forward-only; add a new `NNN_*.sql` file for a schema change, never edit an already-applied one. `dbstore migrate new <name> --project db.dbstore.json` scaffolds the next one. |
| `queries/*.sql` (not `queries/*.sql.go`) | **Hand-written.** sqlc query definitions — the SQL the generated Go wraps. |
| `queries/*.go` | **Generated by sqlc.** Never hand-edit — `make generate` overwrites it. Each file starts with `// Code generated by sqlc. DO NOT EDIT.` |
| `db.dbstore.json`, `queries.gen.json` | Project/sidecar config for the generator - see below. |

## Regenerating

```
make generate          # from the repo root - regenerates only if stale
```

`build-controller`/`test-controller` already depend on `generate`, so this
runs automatically before either — you only need it standalone after editing
`schemas/db/*.sql` or `queries/*.sql` and wanting to see the generated diff
without a full build.

Under the hood: `queries.gen.json` (a [`../../../tools/go-deps`](../../../tools/go-deps)
sidecar) declares the generator command as `go run ../../../tools/dbstore
generate --project db.dbstore.json` — see [`../../../tools/dbstore`](../../../tools/dbstore)
for what that actually does (sqlc under the hood, via a temp `sqlc.yaml` it
writes itself).

## Adding a migration

```
cd controller/internal/dbstore
go run ../../../tools/dbstore migrate new add_foo_column --project db.dbstore.json
```

Writes `schemas/db/00N_add_foo_column.sql` with `-- +goose Up`/`-- +goose
Down` stubs. Migrations apply automatically on every `Open()` (see
`migrate.go`) — there's no separate "run migrations" step in normal use.

## The `002` migration (segments + clips)

`002_segments_and_clips.sql` split the original one-row-per-file `clips` table into:

- **`segments`** — one row per recorded file (what `clips` used to hold), plus a `clip_id` and
  `end_ms`. The migration copies every existing `clips` row straight in with `clip_id = ''`.
- **`clips`** (rebuilt) — the user-facing gallery item: a contiguous run of segments, holding
  the `active`/`trashed`/`purged` lifecycle and aggregate `started_at_ms`/`ended_at_ms`/
  `segment_count`/`size_bytes`.

It is **forward-only and not cleanly reversible** — the down migration drops both tables
without reconstructing the old shape, and it **intentionally drops per-segment trash/purge
state** (near-meaningless at ~10s granularity): everything already synced becomes one `active`
clip. Right after the migration, `Open()` calls `RegroupUnassignedSegments(GroupingGapMs)`
(`regroup.go`) once to assign a `clip_id` to every carried-over segment and create the `clips`
rows — greedy single pass per phone in time order, grouping segments whose gap is
`<= GroupingGapMs` (500ms). It's idempotent: it only touches `clip_id = ''`, so it's a no-op
on every subsequent boot.
