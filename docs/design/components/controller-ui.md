# controller — frontend — software design description

## 1. Introduction

### 1.1 Purpose

Describe the controller's UI: a Preact SPA in the embedded webview, rendering a read view over
the controller's SQLite state plus live status/preview from the phones.

### 1.2 Scope

Covers `controller/frontend/` — `src/main.tsx`, `src/App.tsx`, `src/screens/*`,
`src/components/*` (except the live/camera pieces, which are
[`controller-live-and-camera.md`](controller-live-and-camera.md)), `src/api.ts`, `src/lib/*`,
`src/types.ts`, `src/style.css`, `generated/wailsjs/`.

### 1.3 Context

The frontend's only backend is the Wails binding surface on `App` (see
[`controller-runtime.md`](controller-runtime.md)). It reads DB-backed data and does not talk to
phones directly (except the same-origin live proxy).

### 1.4 Definitions

| Term | Meaning |
|---|---|
| screen | one top-level route: Fleet, Phone detail, Gallery, Trash, Add phone |
| master-detail | a list beside an inline detail pane, not a modal/lightbox |
| stable key | screens keyed by bare route so navigation/selection doesn't remount/refetch |
| selection key | `phoneId|clipId` — identifies a selected clip across screens |
| generated bindings | `generated/wailsjs/` — Wails' output, never hand-edited |

## 2. Design overview

A single `useState<AppState>` router: `navigate()` merges a partial `AppState`; screens keyed by
bare route so navigation and selection don't remount or refetch, and stale data stays painted
during a refetch. Five screens over a shared nav shell, plus shared clip-grid / clip-player
components.

## 3. Detailed design

### 3.1 Design entities

| Entity | Responsibility |
|---|---|
| `main.tsx` | entry point, mounts `<App/>`. |
| `App.tsx` | top-level router/state (one `useState<AppState>`); `navigate()` merges a partial state; `phone` reuses the `fleet` key. Screens refetch only on real input changes. |
| `screens/` | `Fleet.tsx` (master list + inline `PhoneDetail`), `PhoneDetail.tsx`, `Gallery.tsx`, `Trash.tsx`, `AddPhone.tsx`. |
| `components/` | `Shell.tsx` (nav rail + slot); `ClipTiles.tsx` (day-grouped grid, shift/ctrl multi-select, shared by Gallery/Trash); `ClipPlayer.tsx` (keyed `<video>` walking a clip's segments as a playlist; with `autoplay`, plays through to the next clip across its remount); `PhoneCommandBar.tsx`, `ConfigForm.tsx` (editable), `StatusPanel.tsx` (read-only), `BatteryIcon.tsx` (cell/bolt glyph, never text). Live/camera components are separate — see [`controller-live-and-camera.md`](controller-live-and-camera.md). |
| `api.ts` | thin typed re-export of the generated Wails bindings under stable names, so a binding-shape change is a one-place fix. |
| `generated/wailsjs/` | Wails' generated bindings — `wailsjsdir` in `wails.json` points here so generated code is physically separated. Regenerated by `wails build`/`dev`. |
| `lib/` | `format.ts` (byte/duration/status labels), `clips.ts` (day-grouping + the `phoneId|clipId` key), `icons.tsx` (inline SVG icon set). |
| `style.css` | plain hand-written CSS, imported once; visual language ported from the mock. |

### 3.2 Dependencies

- The `App` Wails bindings (via `api.ts`).
- Preact + Vite (`@preact/preset-vite`).
- The live/camera component for the Phone-detail live section.

### 3.3 Interfaces

- **Provided:** none (leaf UI).
- **Required:** the Wails binding surface; the same-origin `/archive/*` and `/live/<phoneID>/*`
  asset routes.

### 3.4 Data

- `types.ts` — shared `Route` / `AppState` types. No persistence; all data is fetched from `App`
  per screen and cached in component state.

### 3.5 Processing and behaviour (screens)

- **Fleet** — master-detail; card shows phone name + status + battery glyph only ("unreachable"
  is a status value). Aggregate disk-usage stat in the header.
- **Phone detail** — command bar + editable config form + read-only status panel + battery
  glyph. `SetConfig` renames the local `phones` row on a `deviceName` change (`UpdatePhoneName`)
  so the name propagates through Fleet / Gallery filters / clip attribution.
- **Gallery / Trash** — master-detail, not a lightbox. Gallery: per-phone filter chip row,
  `autoplay` advance. Trash: no chip row, no autoplay (stops at clip end), Restore + Delete
  fabs, `Empty trash` gated behind a count-naming confirm. Shift/ctrl multi-select, arrow-key +
  Delete-key nav.
- **Add phone** — paste view (two fields, full-URL autofill into either) default; QR link
  (deferred). "Connecting…" → inline error distinguishing unreachable address vs bad invite, or
  a success card.

## 4. Design rationale and decisions

- **Master-detail everywhere; stable keys; minimal Fleet card** —
  [`0012`](../decisions/0012-ux-shape.md): autoplay-advance needs the grid selection
  to stay visible, which a modal makes awkward; the old remount-on-nav caused a loading flash on
  every selection.
- **UI reads the DB, not the phones** —
  [`0011`](../decisions/0011-controller-runtime-and-state.md): keeps the UI responsive
  during sync.
- **Generated bindings in a dedicated directory** —
  [`0001`](../decisions/0001-repository-and-build.md).
- **Not built (deferred):** QR webcam viewfinder; the mock's custom scrubber (native
  `<video controls>` used instead); bulk arm / bulk stand-down; a continuously-updating status
  poll. Tracked in [`../../status/`](../../status/).
- **Placeholder theme** — [`../../status/visual-language-pass.md`](../../status/visual-language-pass.md).
